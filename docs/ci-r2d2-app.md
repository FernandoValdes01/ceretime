# Identidad de R2D2 en GitHub

El resumen y los comentarios inline usan el nombre R2D2. Cada PR mantiene un único comentario de resumen, que se edita al recibir nuevos commits o al repetir una ejecución. La imagen del avatar está en `.github/assets/r2d2.jpg`; no se repite dentro del comentario y no pertenece a Web ni Mobile. El resumen muestra la nota real como `Confidence Score: N/5`, una tabla de riesgo, hallazgos y estado, el título del commit enlazado y el SHA completo en los datos de ejecución plegados. Elimina las negritas de la prosa y el pie publicitario del reviewer. También ordena los comentarios antiguos de esa identidad asociados a sus reviews de IA identificadas en la PR, conservando su SHA original. Los bloques de sugerencias y el código permanecen intactos. Los cuerpos de las reviews anteriores de ambas identidades se ocultan mediante un marcador sin contenido visible; sus hallazgos inline y su asociación al commit se conservan. GitHub mantiene los eventos históricos de review, pero el informe completo vive en un solo comentario.

## Autor y avatar

El autor de GitHub depende del token usado para publicar. `GITHUB_TOKEN` pertenece a la App de GitHub Actions y publica como `github-actions[bot]`; cambiar un título no cambia esa identidad. Para usar una identidad propia, [registra una GitHub App](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/registering-a-github-app) y autentica mediante su token de instalación.

1. Abre [Developer settings → New GitHub App](https://github.com/settings/apps/new). La App de esta integración se llama `R2D2-reviewer`, con slug `r2d2-reviewer`; su autor es `r2d2-reviewer[bot]`. Usa la URL del repositorio como Homepage URL. El nombre visible del resumen sigue siendo R2D2.
2. Desactiva Webhook y no solicites autorización de usuarios. El workflow de Actions ejecuta el reviewer; la App aporta su identidad.
3. Concede solo Repository permissions: Contents `Read-only`, Pull requests `Read and write` y Commit statuses `Read and write`. Metadata `Read-only` es implícito. No necesita permisos de administración, Issues, Checks ni escritura de Contents.
4. Registra la App privada y configura `.github/assets/r2d2.jpg` como logo en sus ajustes. Instala la App seleccionando únicamente `ceretime`.
5. Guarda el App ID como secret `R2D2_APP_ID`. Genera una private key y guarda su contenido exclusivamente en el secret `R2D2_APP_PRIVATE_KEY` de GitHub Actions. No guardes el archivo PEM en el repositorio ni envíes su valor al chat o a comentarios.
6. Ejecuta de nuevo `AI Code Review` en la PR de TI4-45. Comprueba el autor propio y el avatar en una review nueva, su SHA y su status. Las publicaciones históricas conservan su autor original.

La integración usa `actions/create-github-app-token`, fijada por SHA, para generar un token limitado al repositorio y a esos tres permisos. Entrega el token a los scripts del motor y de publicación. La Action de tokens lo revoca al terminar el job. El workflow no imprime credenciales y mantiene `persist-credentials: false` en el checkout.

Si faltan los secrets de la App, el reviewer sigue funcionando con `GITHUB_TOKEN`: el contenido muestra R2D2, pero el autor todavía es `github-actions[bot]`. No se presenta ese modo como una identidad propia comprobada. Si los secrets existen pero la autenticación falla, se publica un fallo de ejecución; no se considera una review válida.

## Score y transición desde Greptile

El diseño muestra `5/5` cuando una evaluación vigente, completa y sin hallazgos obtiene ese score. No transforma un `0/5` en `5/5` por presentación. Los 24.000 caracteres son un objetivo por bloque, no el límite total de una PR. La ruta por bloques agrega un único resultado, conserva hasta cinco hallazgos sin repeticiones con líneas válidas y solo declara cobertura completa después de procesar todo el cambio elegible. Un fallo necesario, una respuesta inválida o el agotamiento del presupuesto conserva 0/5. Los presupuestos y el flujo incremental están documentados en [protecciones de CI](ci-protections.md). La aprobación humana continúa siendo obligatoria.

El workflow remoto `Sincronizar check de Greptile` fue desactivado mediante la API de GitHub después de retirar sus archivos en esta rama. Su estado consultado es `disabled_manually`. Ya no debe publicar el status antiguo sobre commits nuevos. Los statuses históricos siguen asociados a sus commits; no se heredan al SHA nuevo. Esto no desinstala la GitHub App de Greptile: verifica su instalación y suscripción por separado. No se modificó el ruleset ni se integró directamente en main.

## Conversaciones sobre hallazgos inline

El workflow `ai-review-conversation.yml` escucha `pull_request_review_comment` con actividad `created`. Un integrante con asociación `OWNER`, `MEMBER` o `COLLABORATOR` puede responder directamente debajo de cualquier hallazgo inline creado por `r2d2-reviewer[bot]`; no necesita mencionar al bot. R2D2 contesta en ese mismo hilo mediante el comentario raíz, incluso cuando la respuesta humana contesta a otra respuesta del hilo. Los comentarios generales de la PR no activan este flujo.

La consulta usa OpenRouter y `deepseek/deepseek-v4.1-flash` con el hallazgo original, archivo, coordenadas, hunk, hasta diez mensajes anteriores, nueva explicación y contexto mínimo de la PR. Incluye el fragmento de la versión original y el actual con sus coordenadas actualizadas. Los comentarios LEFT se leen en el merge-base histórico guardado en el hallazgo original y los renombres siguen la ruta actual. Si el historial o el contenido faltan, señala evidencia incompleta en vez de recortar HEAD con una línea antigua. R2D2 puede mantener, corregir, retirar el hallazgo o pedir contexto. Debe reconocer explicaciones que demuestren que la observación no aplica. No consulta Linear: las conclusiones que dependan de tareas o decisiones externas se identifican como dependientes del contexto aportado.

La conversación no ejecuta los bloques de revisión, no modifica el Confidence Score ni publica statuses. La siguiente review formal verifica el hallazgo con la explicación humana y el cambio relacionado, reutiliza unidades intactas y conserva el hilo; la aprobación humana TI4 sigue siendo obligatoria. Se excluyen bots, PR Draft, forks y comentarios que no respondan a un hilo del bot. Un marcador por respuesta humana evita duplicados al reintentar el evento; cada evento tiene su propio grupo de concurrencia para conservar respuestas distintas. Admite PR internas con cualquier base. Se verifican nuevamente el SHA head, el SHA de base y el nombre de base antes de publicar y se descartan conclusiones si cambia alguno durante la consulta.

Este workflow utiliza solamente `contents: read` y `pull-requests: write`, tanto para Actions como para el token de la App. No utiliza un token alternativo de GitHub Actions si falla la App. Conserva los secrets existentes sin exponerlos. Cada respuesta consume como máximo dos llamadas, con salida máxima de 1.200 tokens por llamada, timeout de 30 segundos y un límite de 18.000 caracteres para el contexto enviado como JSON. Los textos largos se recortan con una señal explícita de contexto parcial; si se supera el presupuesto, solicita una explicación más breve. Un fallo del proveedor devuelve una petición de reintento en el mismo hilo.
